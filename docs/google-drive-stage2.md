# Google Drive — этап 2: безопасная авторизация и сетевой транспорт

Дата: 10.10.2026. Статус: проектирование и подготовка к реализации; **реальное подключение не выполнено**.

## Исходная база

Этап 1 объединён в main через PR №6 (merge `2c0f6cb21acae3b60a25f45ecef447a67df25b4e`).
Существуют `GoogleDriveDocumentSource` и интерфейс `GoogleDriveTransport`.
`DocumentRepositoryFactory` по-прежнему регистрирует только `AssetsDocumentSource`.
Текущий AndroidManifest не содержит INTERNET; существующие PDF/индексы, Room и UI не изменяем до отдельной проверки.

## Архитектура авторизации

1. Использовать системный браузер / Custom Tabs и OAuth 2.0 Authorization Code с PKCE (S256). Не использовать embedded WebView, пароль пользователя или implicit flow.
2. Выбрать Android OAuth client ID и зарегистрировать соответствующие Android package name и SHA-1 сертификата приложения в Google Cloud Console. Для выбранного механизма redirect URI заранее проверить требования Google и библиотеки; не придумывать URI.
3. Запрашивать минимальный scope: предпочтительно `https://www.googleapis.com/auth/drive.file` для файлов, созданных или открытых через приложение. Если требуется читать произвольные существующие файлы пользователя, сначала отдельно согласовать UX выбора через Google Picker и требуемые scope/verification; `drive.readonly` не включать по умолчанию.
4. Проверять `state`, `code_verifier`, `code_challenge`, redirect URI и ошибки callback. Не логировать auth code, access token, refresh token, заголовок Authorization и содержимое документов.
5. Токены хранить в защищённом приватном хранилище Android с использованием Android Keystore для ключевого материала; не помещать в Room, git, ресурсы или backup. Предусмотреть отзыв доступа, выход из аккаунта и безопасное обновление токена с синхронизацией конкурентных запросов.
6. Транспорт должен возвращать поток без загрузки всего PDF в память, использовать connect/read timeouts и закрывать HTTP response вместе с InputStream; обрабатывать 401 (обновить токен один раз), 403, 404, отмену и сетевые ошибки.
7. Метаданные пары PDF + search index должны приходить из доверенного manifest, содержащего оба file ID, SHA-256 и ревизию пары. Drive MD5 / version одного файла не заменяют доверенный manifest. Проверять хеши перед атомарной активацией, сохранять старую offline-копию при сбое.

## Границы этапа и критерии готовности

- Подэтап 2A: согласовать OAuth-клиент, scope и выбор файлов; реализовать абстракции auth/session без секретов в коде.
- Подэтап 2B: авторизованный HTTP-транспорт и проверяемый manifest; unit-тесты 401/403/404, retry, таймаутов, закрытия потока и отказа при неправильных SHA.
- Подэтап 2C: отдельная opt-in регистрация в factory, Android runtime тест, ручная проверка реального аккаунта, больших PDF и offline-open.
- На каждом PR выполнять GitHub Actions `assembleDebug` + `testDebugUnitTest` + валидацию каталога.
- До прохождения runtime-проверки не включать Drive по умолчанию и не объединять экспериментальную реализацию с main.

## Решения, требующие участия владельца

- Google Cloud OAuth client ID / конфигурация Android приложения и SHA-1 подписи debug/release.
- Откуда должны выбираться документы: только созданные/выбранные приложением (drive.file) или произвольные файлы Google Drive (потребует отдельного анализа scopes).
- Источник доверенного manifest для каждой пары PDF + индекса.

Не добавлять реальные токены, client secret или приватные идентификаторы файлов в репозиторий.
