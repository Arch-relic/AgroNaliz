# AgroNaliz Agent Core v1 — этап 1

Статус: управляющий валидатор и контракт, без автоматического исполнителя Codex.
Этап реализован по утверждённому пользователем заданию «Agent Core v1.0».
Новые функции приложения, Room24, backup, MAIN/TEST signing, production admission,
существующие workflows и AGENTS.md не меняются. Технические отчёты остаются в
`docs/codex-handoff.md`; этот документ описывает управляющий протокол.

## Данные и жизненный цикл

Задачи: `agent_core/tasks/AGN-N.json`, JSON Schema Draft 2020-12
`agent_core/schemas/task-v1.json`. Пустой каталог означает отсутствие зарегистрированных
задач, а не разрешение на разработку. Синтетическая задача создаётся функцией
`task()` в `tests/agent_core/test_core.py`, не выдаётся за реальный Issue или approval.

Обязательны ID, тип, Issue проекта, числовой GitHub ID исполнителя, состояние,
текущая редакция, массив редакций с названием/описанием/критериями/операциями/
ограничениями/рисками, история состояний и причины, решения и ссылки на результаты.
Ссылки на ещё не созданные ветки/коммиты/проверки/PR представлены пустыми массивами.
`decisions` хранит варианты, выбранный вариант, причину, дату и ID редакции.
Причины отмены и блокировки находятся в обязательном `history[].reason`.

Редакция — объект `spec` и SHA-256 `hash`. Канонизация v1:
`json.dumps(spec, sort_keys=True, separators=(',', ':'), ensure_ascii=True, allow_nan=False)`
в UTF-8. Массивы упорядочены, включая операции. Все функциональные требования и
интерфейс описываются в `spec.description`/`acceptance`; их изменение — новая редакция
с новым ID и хешем. Ссылки на изменяемые внешние документы не заменяют содержание ТЗ.
Дубликаты ключей JSON, неизвестные поля, неверные даты/хеши отклоняются.

`revisions`, `history`, `decisions` дополняются, но не переписываются и не сокращаются
относительно доверенной базы. ID/Issue/тип/исполнитель неизменяемы. Смена исполнителя
требует новой задачи. Время переходов не убывает. Предыдущие согласования сохраняются
в истории как ссылки `approval_run` на независимо проверяемые запуски GitHub Actions.

| Из состояния | Допустимые состояния |
| --- | --- |
| регистрация | proposed |
| proposed | awaiting_approval, blocked, cancelled |
| awaiting_approval | approved, blocked, cancelled |
| approved | implementing, awaiting_approval, blocked, cancelled |
| implementing | review, awaiting_approval, blocked, cancelled |
| review | done, implementing, awaiting_approval, blocked, cancelled |
| blocked | awaiting_approval, cancelled |
| done, cancelled | нет |

`approved` требует проверенного согласования; `implementing`, `review`, `done` требуют
действующего согласования той же редакции. Изменение редакции разрешено только через
`awaiting_approval` (или первичную регистрацию). Блокировка, отмена и возврат к
согласованию снимают допуск. Возобновление после блокировки требует нового approval.
`done` — завершение задачи, не merge и не публикация.

## Approval Gate и доверенная граница

Корень доверия: репозиторий `Arch-relic/AgroNaliz`, main, числовой GitHub ID владельца
`240867647` (независимо прочитан через GitHub API), код gate из базовой ветки.
Смена владельца/протокола требует отдельного review. Login/comment/label не являются
доказательством. Исполнитель с ID владельца не может согласовать собственную задачу.

Порядок после первого включения workflow владельцем:

1. Зарегистрировать метаданные задачи отдельным PR, довести до `awaiting_approval`.
   Владелец отдельно решает о merge этих метаданных в main. Агент merge не делает.
2. Владелец читает точное ТЗ на main, вычисляет хеш редакции и хеш списка операций
   функцией `digest`. Вручную запускает `Agent Core` строго из main с `mode=approve`,
   `task`, `spec_hash`, `operations_hash`, `executor_id`, `sequence=len(history)`.
   Параметры лишь запрос: workflow сверяет их с задачей на неизменяемом `GITHUB_SHA`.
3. Успешный **первый** запуск владельца образует свидетельство. Run name содержит
   `approve:<task>:<spec hash>:<operations hash>:<executor ID>:<sequence>`.
   ID этого запуска записывается в единственный новый переход в `approved`.
4. Gate заново получает запуск через GitHub API: repo/head repo, workflow ID/path,
   actor/triggering_actor IDs, workflow_dispatch, main, attempt=1, completed/success
   и точный run name должны совпасть. Из commit `run.head_sha` независимо читается
   задача: Issue/тип/исполнитель, редакции и точный префикс истории должны совпасть.
   Файл PR сам по себе не подтверждает полномочия.
5. Перед **каждым отдельным действием** будущий доверенный исполнитель вызывает
   `authorize(task, operation)` из доверенной версии core. Передавать `api` или
   `actor_id` нельзя. Транспорт закреплён в `agent_core.check` на GitHub API и REPO.
   Идентичность читается из GitHub run API и сверяется с GitHub runner context:
   main workflow ref/path/ID, repo/head repo, SHA, dispatch, first attempt, active run,
   actor=triggering_actor и GITHUB_ACTOR_ID. PR/ветка/завершённый run не подходят.
   Отсутствие контекста, поля или API приводит к отказу. Это не Python sandbox:
   процесс, код, GH_TOKEN, импорты и runner environment должны быть доверенными;
   недоверенный исполнитель не должен управлять ими или исполняться в этом процессе.
   Моки/подмена модулей допустимы только в unit-тестах, не на границе полномочий.
6. Получить SHA main через Git refs API; прочитать JSON задачи строго по этому SHA.
   Полностью сравнить с переданным снимком, заново проверить схему/историю/grant,
   актуальные состояние, редакцию и scope; повторно прочитать SHA main. Любое
   расхождение, смена SHA (даже от постороннего коммита), отсутствие задачи,
   невалидный Base64/JSON, недоступность или неоднозначность — отказ без fallback.
   Историческое run.head_sha остаётся доказательством утверждения, но больше
   не служит источником актуального допуска. Успешная проверка не кэшируется.

**Отзыв действует после фиксации изменения задачи в main.** Незамерженный PR,
комментарий или метка не отзывают допуск автоматически. Разрешение проверяется
перед каждым действием; оно не является долгоживущим token/lease и не может
немедленно остановить уже запущенную операцию. Изменение main после последнего
чтения возможно; аварийная остановка/атомарное исполнение — отдельный будущий этап.
Текущий workflow не вызывает автоматический исполнитель или authorize для действий:
контекст намеренно ограничен доверенным Agent Core main dispatch. Интеграция
исполнителя и допустимые execution workflows требуют следующего согласованного этапа.

Approval одноразово привязан к позиции истории и её префиксу; повторное использование
для нового approval/другой задачи/редакции/исполнителя отвергается. Действующий допуск
может использоваться для технических исправлений **только** при наличии
`technical_fix` в утверждённых операциях и в рамках ТЗ. Новая функция/изменение UI —
новая редакция. Старый approval не переносится. Удалённое свидетельство GitHub
приводит к отказу, даже если историческая ссылка осталась в JSON.

Операции `room`, `backup`, `signing`, `production_policy`, `merge_main`, `publish_apk`
в этапе 1 всегда запрещены, в том числе при их добавлении в список операций.
Их отдельный протокол разрешения не реализован. Этот gate не выдаёт разрешение
на merge, APK, Release или изменение защищённых компонентов.

## GitHub Actions и первое включение

`.github/workflows/agent-core.yml` разделяет:

- `pull_request`: unit-тесты недоверенного кода, contents:read, без переданного
  GH_TOKEN, секретов и сохранения checkout credentials. Это не выдача полномочий.
- `pull_request_target`: код/схемы только из точного base SHA. PR читается как JSON
  через GitHub API, не checkout/import/run кода PR. Проверяется append-only история,
  grants, полный список изменённых файлов, согласованность head/base до и после
  проверки. Удаление задач и подмена управляющего кода/схем/workflows, включая rename,
  отклоняются. Запрос на изменение самого gate требует отдельного review владельца;
  workflow не может выдать разрешение на собственную замену.
- `workflow_dispatch`: только owner/main/attempt 1, выдаёт проверяемое свидетельство
  согласования или проверяет контракт начала сессии. Пишущих полномочий нет.
- `schedule`: понедельник 06:17 UTC, только проверка контракта weekly на main.

Checkout закреплён SHA, persist-credentials=false. Trusted job имеет только
contents:read/actions:read/pull-requests:read, timeout 5 минут. Production secrets,
запись веток, коммиты, merge, artifacts APK и постоянный сервер отсутствуют.
API 403/404, неполные результаты, недоступный fork SHA — отказ, не обход проверки.

**Bootstrap:** новый pull_request_target workflow пока отсутствует в main, поэтому
этот Draft PR проверяет новый код unit-тестами; доверенный протокол станет активен
после отдельного review/merge владельцем. Нельзя подменять это утверждением о
проверенном реальном owner approval. После merge нужен отдельный реальный прогон
owner/main с тестовой задачей и отрицательные проверки; здесь он не выполнялся.

По наблюдению API на этапе разработки main имеет `protected:false`, rulesets `[]`;
отдельный branch-protection endpoint вернул 403 интеграции. Настройки не менялись.
Рекомендуется отдельно согласовать required check доверенного workflow и защиту
изменений governance. Пока required checks не установлены, статус workflow носит
проверочный характер: он не способен запретить владельцу/пользователю с write
обойти CI. Даже при наличии защиты проверка не доказывает семантическое соответствие
произвольного Android diff тексту ТЗ. Этап 1 проверяет зарегистрированные задачи;
не вводит обязательную привязку всех существующих Android PR к новой системе и
не меняет текущий процесс выпуска. Автоматического исполнителя ещё нет.

## Контракт рекомендаций

`agent_core/schemas/recommendation-v1.json`, каталог `agent_core/recommendations/`:
ID, schema_version, trigger (`session_start`/`weekly`), created_at, title, rationale,
priority, evidence (ссылки/репозиторные пути), proposed_operations, status=proposed.
Из рекомендации автоматически не создаётся approval или задача в реализации.
Схема проверяется и при PR. Важность не предоставляет полномочий.

Начало сессии: контракт ручного `workflow_dispatch mode=session_start` владельцем
после review/merge. Автоматический hook Codex не подключён. Еженедельный schedule
проверяет схему на синтетической записи в памяти и точное расписание; результат
не выдаётся за рекомендацию ИИ. Генерация, уведомления, дополнительные интеграции
и фактический вызов исполнителя требуют следующего согласованного этапа.

## Воспроизводимая проверка

```bash
python3 -m pip install -r agent_core/requirements.txt
python3 -m unittest discover -s tests/agent_core -v
python3 -m agent_core.check local
python3 -m unittest discover -s docs -p 'test_*.py' -q
```

`local` без GH_TOKEN не может подтвердить approved-задачи; пустые каталоги проходят
только структурную проверку. `GH_TOKEN`, если предоставлен для live-read, должен
иметь лишь read-доступ; токен не хранить в файлах задачи/отчётах.
Тесты используют синтетический API, не production secrets или пользовательские данные.

## Решение этапа 1

Варианты: комментарии/метки, подпись приватным ключом, ручной owner/main dispatch.
Выбран dispatch: GitHub предоставляет идентичность и неизменяемую привязку запуска;
не требуется новый приватный ключ, сервер, secret или запись из workflow.
Комментарии/метки не дают надёжной области разрешения; отдельный signer усложнил бы
безопасную выдачу/хранение/отзыв ключей. Цена выбора — предварительное review/merge
метаданных владельцем, зависимость от доступности GitHub и fail-closed при удалении
свидетельства. Редакция данного этапа определена заданием пользователя; история
последующих решений по задачам хранится append-only в task JSON.
