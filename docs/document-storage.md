# Каталог технических документов «АгроНализ»

## Состояние первого этапа

Добавлен независимый каталог 20 существующих документов. Действующие экраны,
PDFView, поиск, подсветка, навигация и Room не изменены. Каталог пока не вызывается
из Activity: он является основой будущего DocumentRepository.
Новые зависимости, Google Drive API и Firebase SDK не подключены.

Модели находятся в `ru.fo6osik.workjournal.documents`:

- `DocumentDescriptor`: постоянный `documentId`, название, ревизия комплекта,
  SHA-256 PDF и индекса, список расположений.
- `DocumentSource`: Assets, AndroidSaf, GoogleDrive, FirebaseStorage.
- `DocumentCatalogData`: версия формата каталога и документы.
- `DocumentCatalog.load(assetManager)`: загрузка `documents/catalog.json`,
  проверка структуры, существования asset-индексов и их известных SHA-256.
- `DocumentCatalog.parse(json)`: разбор и структурная проверка без чтения файлов.
- `validate(catalog)`: проверка моделей, доступная обычным JVM-тестам.
- `verifyAssetIndexes(catalog, openAsset)`: потоковая проверка индексов.

Ошибки структуры вызывают IllegalArgumentException; ошибки JSON и чтения
сохраняют исходный тип исключения. Проверяющий код будущего репозитория должен
преобразовать их в понятные пользователю состояния.

## Формат и идентификаторы

`schemaVersion: 1` — версия формата каталога, **не ревизия документа**.
Идентификаторы назначены один раз по текущим именам файлов. В дальнейшем они
не меняются при переименовании PDF или смене провайдера.

Каталог содержит четыре руководства (`nova_340_manual`, `lada_vesta_sw_manual`,
`kirovets_k424_manual`, `belarus_1021_3_manual`), диагностику
`ymz_5340_536_diagnostics` и 15 бюллетеней `s300_<номер>_be`:
19, 20, 21, 24, 26, 27, 29, 31, 32, 33, 34, 35, 36, 37, 38.
Названия и asset-пути соответствуют VehicleDetailsActivity и
Nova340BulletinsActivity. Для каждого документа явно задан путь индекса.

Пример расположения:

```json
{
  "type": "assets",
  "pdfPath": "manuals/nova_340_manual.pdf",
  "searchIndexPath": "manuals/nova_340_manual_search.json"
}
```

Другие типы уже поддерживаются моделями и парсером, но реальные привязки пока
не заданы:

| type | Поля |
| --- | --- |
| androidSaf | pdfUri, searchIndexUri — content URI |
| googleDrive | pdfFileId, searchIndexFileId — ID файлов, не публичные URL |
| firebaseStorage | bucket, pdfObjectPath, searchIndexObjectPath |

Расположения не содержат токенов, паролей и ключей. Порядок источников пока
не определяет стратегию загрузки: её реализует будущий репозиторий.
SAF URI и личные cloud-привязки следует сохранять в приватных настройках
устройства; постоянное разрешение SAF оформляется отдельно при выборе файла.

## Ревизии и контрольные суммы

Оригинальных PDF в checkout нет. `pdfSha256` всех 20 записей перенесены
из предоставленного списка `docs/pdf-sha256-local.txt` ветки `feature/pdf-sha256`
(коммит `eeca56b6cd2f421fe2af520c4916ef18271f684e`, blob
`66fea21d7af5f010b96a1208acbb4fb169b6e15f`). Список сохранён без изменений.
Сопоставление выполняется только по полному пути: к asset-пути каталога
добавляется точный префикс `app/src/main/assets/`; basename и порядок не используются.
`revision` остаётся `null` у всех документов: хеши не создают ревизию.
`searchIndexSha256` рассчитан по фактическим байтам существующего файла.
При изменении индекса хеш обновляется после проверки, а не отключается.

Известный хеш индекса подтверждает его целостность, но **не подтверждает**,
что отсутствующий PDF соответствует его тексту и координатам. Перед первым
подключением облачных PDF нужно независимо пересчитать их SHA-256, сверить
оригиналы и индексы и назначить реальную ревизию согласованного комплекта.
Хеши из предоставленного списка здесь не пересчитывались по PDF: файлов нет.

Индексы имеют `version: 4` и `coordinateSystem: normalized_page`; это отдельный
формат, не ревизия PDF. Текущий каталог не разбирает текст и координаты индекса:
проверка их семантики и соответствия страницам PDF относится к этапу
репозитория. Существующие поисковые JSON не изменялись.

## Проверки

Проверяются версия схемы, непустой каталог, уникальность и формат ID,
названия, необязательные непустые ревизии и 64-символьные lowercase SHA-256,
наличие источников и отсутствие точных дубликатов.
Для assets проверяются уникальные пути, отсутствие абсолютных путей и
`..`, расширение PDF и точное соответствие `<имя>_search.json`.
Существование PDF намеренно не обязательно. Индексы должны существовать;
`load()` проверяет их хеши, читая по одному потоку без загрузки всех индексов
в память. Этот ввод-вывод следует выполнять вне UI-потока.

Для остальных провайдеров проверяется только синтаксис расположений.
Наличие файлов, OAuth, права SAF, Storage Rules и сетевой доступ этим этапом
не проверяются. Известный pdfSha256 хранится как ожидаемое значение;
LocalDocumentStore сверяет фактические байты при установке и открытии копии.

JVM-тесты покрывают валидные и ошибочные модели, соответствие путей,
провайдеры, отсутствующие/повреждённые индексы и закрытие потоков.
Парсер использует платформенный org.json; его нельзя напрямую выполнять
обычным локальным JVM-тестом с Android stub без отдельной реализации JSON.
Для проверки настоящего каталога без новых зависимостей используйте:

```bash
python3 docs/validate-document-catalog.py
python3 -m unittest discover -s docs -p 'test_validate_document_catalog.py'
```

Скрипт проверяет полноту 20 PDF-хешей, lowercase-формат SHA-256, уникальность
путей/хешей в этом наборе и точное соответствие каталогу и исходному списку.
Для каждого индекса сверяются байты с сохранённым searchIndexSha256, формат
v4/normalized_page, положительные уникальные номера страниц, строковый текст,
смещения слов в единицах UTF-16 (как в Kotlin) и конечные координаты от 0 до 1.
Ссылки и названия сверяются с действующими экранами. При наличии локальных PDF
их хеши вычисляются потоком блоками по 8192 байта; отсутствие файла допускается.
Максимальный номер страницы выводится, но не сверяется с PDF без его байтов.
Структурная корректность и хеши двух файлов не доказывают совместимость содержимого.

Сборка в подготовленной облачной среде:

```bash
cd /workspace/AgroNaliz
source /workspace/agronaliz-env.sh
agrogradle :app:assembleDebug
agrogradle :app:test
```

## Следующие этапы и работа через AndroidIDE

1. DocumentRepository и локальное постоянное хранилище согласованных пар PDF/JSON.
2. Проверка хешей PDF, атомарная активация ревизии, офлайн-открытие.
3. Подключение documentId к текущим экранам без замены PDFView и поиска.
4. Авторизация и загрузка частных файлов Google Drive.
5. Адаптер Firebase Storage за тем же контрактом репозитория.

Для первого пользователя предпочтительны небольшие проверяемые изменения.
Код, каталог и документация синхронизируются через GitHub после проверки.
PDF остаются исключёнными из Git. Токены, SAF-привязки, ключи подписи и личные
конфигурации нельзя добавлять в репозиторий. AndroidIDE и другие среды должны
использовать совместимую подпись для обновления APK без потери локальных данных.

Индексы содержат текст руководств и сейчас хранятся в Git/assets. Каталог не
меняет эту модель приватности; перенос индексов в закрытое хранилище должен
быть отдельным согласованным этапом.
